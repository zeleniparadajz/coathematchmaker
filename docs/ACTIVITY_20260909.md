# Player Activity and Automatic Unavailability

## Behaviour

- Player cards, the compact player list and profiles show the last recorded visit
  as a local date and time. Missing history is explicitly shown as unknown.
- Successful login and authenticated API requests record the requesting player's
  activity using server time. Updating someone else's profile, score or image
  does not update that person's activity.
- The mobile app sends a heartbeat immediately after login/resume and once per
  minute while signed in and in the foreground. It stops in the background and
  after logout. Network failures are retried without interrupting the app.
- Timestamp writes are throttled to once per minute. The stored date is therefore
  approximate to a minute, not an online/offline indicator. Offline app use cannot
  be observed by the server. Older app versions are covered by authenticated API
  requests, even without the dedicated heartbeat.

## Admin Setting

League settings contain an automatic-unavailability switch and a number of days
(1-365). The database field is `inactivityDays`; `0` disables the rule and is the
default. Enabling the switch initially proposes 30 days, which the admin can edit.
Only the global admin can save this setting; tournament managers cannot.

At startup, every five minutes, after a policy change and before creating a
challenge, the backend applies the policy. At the inclusive elapsed-day boundary
it changes `playStatus` from `available` to `unavailable`, records
`playStatusSource: inactivity` and updates `playStatusUpdatedAt`.
It never suspends the account or alters rankings, matches, tournament entries or
manually unavailable players. Existing admin challenge permissions remain intact.

A return visit does not automatically make the player available again. The player
can choose availability in the existing availability screen; manual status changes
clear the inactivity marker. Disabling the rule also does not reset existing
unavailable statuses.

## Existing Players and Release

No historical last-visit dates can be recovered. Existing players receive a
one-time `activityTrackingStartedAt` baseline on backend startup; until their
first recorded visit, the inactivity countdown uses this baseline. It is not
displayed as a visit, and restarts do not reset it. New accounts get a baseline
when created. Deleted accounts have both activity timestamps removed.

Deploy the backend first, then release the mobile build. No manual database
migration is necessary and no environment-variable change is required.
After pulling the code on the server, rebuild the API service:

```sh
docker compose up -d --build api
```

The UI and numeric setting are available in MNE and ENG. No app version/build
number was bumped and no production deployment was performed by this change.

## Verification and Rollback

`backend/test/activity.integration.test.ts` uses a unique, isolated local Mongo
database to verify authorization, server timestamps, write throttling, legacy
grace periods, exact boundaries, background sweeps, manual overrides, challenge
protection and deletion. `test/activity_test.dart` covers foreground lifecycle,
offline retries, both languages, responsive layouts and settings persistence.

The prior code is archived in `.local-backups/activity-20260909/before.tar.gz`,
including the completed bilingual feature. Compare later edits before restoring.
New files to remove for a complete code rollback are the activity services,
`lib/widgets/player_activity.dart`, the two activity tests and this document.
Disabling the rule stops future automatic status changes; it intentionally does
not rewrite player statuses already changed. No production database was modified.
